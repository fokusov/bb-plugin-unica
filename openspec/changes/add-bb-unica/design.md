## Context

В текущем `1c-properties` мост использует официальный stdio и метаданные рабочего каталога. Сервер BB уже разрешает окружение потока. SDK предоставляет host entry, агентские инструменты, CLI и форму взаимодействия. `dsh-unica` привязывает процесс к workspace и проверяет две копии одного проекта.

## Goals / Non-Goals

- Цели — самостоятельная установка, совместимый публичный интерфейс, одинаковый выбор рабочей копии редактором и агентом, контролируемый переход.
- Приёмка задач остаётся в BSL Flow. UI ограничен установкой, статусом, политикой и подтверждением операций.

## Decisions

1. **Переиспользовать официальный пакет и текущие рабочие части моста.** BB Core и готовый MCP способны подключить сервер для одного профиля, но им требуется интеграция для адресации окружения, публичных инструментов, политики, подтверждений и миграции из действующего плагина. DSH-адаптер привязан к профилям DSH. Из него берутся модель изоляции и базовые проверки. Если будут перенесены его файлы, сохраняются их лицензия LGPL-3.0-or-later и атрибуция. Для материалов Unica проверяются лицензии конкретных компонентов. Рантайм берётся из официального пакета через его bootstrap и manifest.
2. **Маршрутизировать по окружению BB.** Для потока используются host и путь окружения. Для явного другого проекта и работы без потока используется выбранный источник. Состояние операций привязано к workspace. Число процессов определяется проверкой, сохраняется маршрутизация текущего моста, если проходит изоляция контекста, задач и разрешений.
3. **Выделить данные владения.** Новая политика хранится в `.bb/unica.json` основного источника. При её отсутствии используется совместимое прежнее значение `unicaPolicy` из параметров проекта. Ошибка чтения явной политики блокирует мутации. Новая запись не меняет чужой JSON. Manifest навыков Unica принадлежит новому плагину. Для перехода он читает предыдущий список managed-копий, принимает только помеченные каталоги и справочники. Пользовательские копии сохраняются.
4. **Перенести DAP отдельным проверяемым этапом.** Подключение к запущенному тестовому контуру возможно без `1c-properties`. Для запуска клиентского процесса и сервера отладки используется настройка тестовой цели на машине проекта. Сохранить существующий путь запуска через параметры проекта, используя только локальный доступ к учётным данным и без выдачи их через RPC. Конкретный контракт Launch выбирается после проверки публичного DAP Unica и имеющегося кода. Сценарий Launch входит в приёмку удаления встроенного DAP.

## Migration Plan

Совместимый выпуск `1c-properties` сначала готовит отключение встроенных регистраций. После завершения активных операций выбери внешний режим и проверь отсутствие старого владельца. Затем включи `bb-unica` и проверь новый набор инструментов из нового потока. Активация при конфликте должна остановиться с инструкцией. До включения старого владельца при откате новый отключается, а эффективная политика сверяется с настройками старого владельца и переносится в него при расхождении. Откат при невозможности сохранить политику блокируется.

## Risks / Trade-offs

- Дублирование Unica через нативный пакет провайдера и BB выявляется при проверке нового потока. Поддерживаемый профиль должен показывать ровно один рабочий маршрут.
- Долгие операции и DAP проверяются через отмену и восстановление. Неопределённый итог требует чтения состояния, а не повторного запуска.
- Переходный разрыв между выключением старого владельца и запуском нового допустим с понятным статусом и сохранёнными настройками.
